# Интеграция Nova CRM с Altegio

Сверено с документацией Altegio: заголовок `Authorization: Bearer <partner>, User <user>`; вход пользователя по `login`/`password` возвращает `user_token`; у записи есть поля `attendance` (-1 не пришёл, 0 ожидание, 1 пришёл, 2 подтвердил), `confirmed`, `staff_id`/`staff`, `client`, `services`, `datetime`, `created_user_id`, `create_date`, `last_change_date`, `deleted`; список записей фильтруется по `start_date`, `end_date`, `changed_after`, страницы задаются через `page`/`count`. Формат тела вебхука и `hooks_settings` я ещё раз проверю на первом реальном событии и подстрою разбор.

## Этап 1 — подключение и сырые данные
- Ключи в Secrets: ALTEGIO_PARTNER_TOKEN плюс ALTEGIO_USER_TOKEN или, если токена нет, ALTEGIO_LOGIN/ALTEGIO_PASSWORD (токен будет получаться на сервере).
- Новые таблицы: записи Altegio (последнее состояние, полный payload, флаг удаления), события вебхука (без дублей по X-Hook-Id), сотрудники/врачи Altegio, привязка филиалов, привязка врачей и сотрудников, категории услуг (консультация хирурга / операция / общий приём), задания загрузки истории. Читают только руководитель и РОП.
- Приёмник вебхука; запись меняется только если `last_change_date` новее сохранённой, поэтому события не по порядку и повторы безопасны.
- Раздел «Настройки → Altegio» (только руководитель): статус, последнее событие, события сегодня, ошибки, «Проверить подключение», «Найти мои филиалы», таблица филиалов, привязки врачей и сотрудников, категории, «Зарегистрировать вебхук», «Загрузить историю» с выбранной даты (по умолчанию 01.09.2026) с продолжением после обрыва.
- Ежечасная сверка последних 3 дней по каждому филиалу (24 запуска в сутки).

## Этап 2 — единая база и статусы
- Пациент определяется по телефону; запись связывается с открытым обращением пациента в том же филиале или создаётся новое обращение (источник «Altegio», пометка «создано из Altegio»).
- Направление по филиалу (abd3/asanbay — Хирургия, moskovskaya/abd2 — Общий профиль), уточнение по категории услуги.
- Статусы по ТЗ: запись → этап ≥3, кто записал, дата визита; подтвердил; пришёл → этап ≥5; не пришёл; удалена → отметка в истории; операция → этап 6 / 10 и сумма. Каждое изменение пишется в историю обращения. Переходы назад и ручные данные CRM не затираются.

## Этап 3 — отчёт «Воронка по Altegio»
- Фильтры: период, филиал, направление, врач, сотрудник, источник.
- Показатели по ТЗ, включая переход с общего профиля в хирургию, конверсии и «Кто куда ушёл» (филиалы и врачи: откуда → куда).
- Клик по любой цифре открывает список пациентов; выгрузка в Excel.

## Проверка
После загрузки покажу: записи по каждому филиалу, сколько пациентов совпало с CRM по телефону, сколько врачей и сотрудников не сопоставилось автоматически. 3 этаж, Chat2Desk и текущие отчёты не меняются.

## Что нужно от вас

- Опубликовать приложение до регистрации вебхука, потому что Altegio отправляет события на опубликованный адрес.

## Технические детали
- Серверные маршруты в `/api/public/altegio-webhook` и `/api/public/jobs/altegio-reconcile` (управляемое расписание); вызовы API и логика сопоставления в `*.server.ts`; чистые правила статусов и метрик в `src/lib/altegio.ts` с тестами (замоканный fetch).
- Сопоставление записи с обращением выполняется атомарно на сервере через функцию-ключ, а связь (record_id → lead_id) хранится, чтобы повторы не создавали дубли.
